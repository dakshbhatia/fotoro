# Fotoro wire contract v1 (frozen October 1, 2026)

Import TS types from `@fotoro/contracts`, validation from `@fotoro/contracts/validate`, crypto from `@fotoro/crypto` (await `ready` before synchronous functions). Exact required fields and enums are in `src/models.ts`, `src/auth.ts` and `schema/contract-v1.schema.json`. All objects reject additional fields. Every protocol object has `version:1` except GrantV1 where `version` is an optimistic concurrency revision (>=1). All IDs are UUID; bytes use canonical base64url without padding; SHA256 fields encode 32 bytes; timestamps use UTC ISO8601 ending Z. Schema validation is precompiled standalone JS: no eval/new Function in production.

## Crypto bytes

Signed payload tuple: UTF8(JSON.stringify(["fotoro-signed-v1",kind,accountId,body])). `body` is the base64url of the actual payload bytes. Verify signature before JSON parsing; then validate body against its named schema. Payload kind for photos is `photo-manifest`, grant is `grant`, device approval is `device-approval`. Grant signed body is exactly `{grant,envelopes}`. Clients must compare the verified payload's full content to the posted content, not merely verify an unrelated signature.

Secretstream uses XChaCha20-Poly1305, 32-byte key, 24-byte header. Container starts with header, then repeats big-endian uint32 ciphertext length + ciphertext. Each record has <=4 MiB plaintext, 17 bytes overhead; nonfinal tag MESSAGE (0), final tag FINAL (3). Production importers chunk at 4 MiB except final; the decoder also accepts shorter records. Empty stream is a single zero-byte FINAL record. AAD is UTF8(JSON.stringify(["fotoro-media-v1",photoId,representationId,kind])). Decoder rejects missing final, swapped binding, reordered records, invalid tags/lengths and trailing bytes. Decrypted records before final are provisional; do not claim verified/save until the generator completes and original SHA256 matches. Container metadata header/digest/length must be checked by clients against manifest before accepting it.

WrappedKeyV1 uses XSalsa20-Poly1305 secretbox with random 24-byte nonce and 16-byte MAC, 32-byte vault/recovery key; `wrapKey` also wraps full account bundles. A representation metadata key is 32 bytes. Share sealed key ciphertext is 80 bytes (32 + sealed-box overhead48). Sender Ed25519 signature covers UTF8(JSON.stringify(["fotoro-share-v1",grantId,photoId,senderAccountId,recipientAccountId,sealedMetadataKey])). ShareBinding and envelope include version1. `openShareKey` checks every expected binding field, pinned sender identity/signature and recipient private key. Signing public/private keys are 32/64 bytes; box keys32/32; signature64. Recipient cards pin both public keys through authentic QR/card user choice. Server-provided cards alone do not establish trust.

Golden cross-language bytes: `fixtures/crypto-v1.json`. `media.container` is complete framed ciphertext; `media.chunks` describes header + two framed records, not transport boundaries. `accounts.json` contains **public test secrets only**, two pinned cards, vault/recovery secrets, signing/box private keys and recovery-encrypted bundles. Bundle decrypted JSON fields: vaultKey, boxSecretKey, signingSecretKey. Never regenerate checked-in vectors silently. Tools generation uses random nonces/header/sealed boxes; checked-in results are fixed golden outputs, not a deterministic entropy override. Swift interoperability is a required lane check; workerd libsodium WASM instantiation remains a runtime gate. A Worker may use WebCrypto Ed25519 for canonical signature verification once vector interoperability is proven.

## HTTP routes and bodies

JSON request/response objects use the named types unless specified. API errors are ApiErrorV1; errors include UNAUTHENTICATED401, FORBIDDEN403, GRANT_INACTIVE403, ORIGIN_DENIED403, NOT_FOUND404, VERSION_CONFLICT409, IDEMPOTENCY_CONFLICT409, UPLOAD_INCOMPLETE409, DIGEST_MISMATCH422, INVALID_WIRE400, BODY_MISMATCH400, SOURCE_MISMATCH400. `retryable` is false for these. Requests operate as session actor; supplied owner IDs never authorize a request.

- POST `/v1/uploads/reserve`: ReserveUploadV1 → UploadReservationV1; PUT stagingUrl with exact ciphertext; POST `/v1/uploads/:uploadId/commit` (empty body) → UploadCommitV1. GET `/v1/objects/:objectId` → authorized ciphertext bytes. Immutable final object has no client PUT.
- POST `/v1/photos`: SignedPayloadV1(kind photo-manifest, body PhotoManifestV1) → PhotoManifestV1. GET `/v1/changes?cursor=<opaque>&limit=100` → ChangePageV1. ChangeV1 has cursor, entity photo/grant, entityId, deleted and payload signed bytes/null. Cursor applies atomically with the page; tombstones contain deleted:true and payload:null.
- POST `/v1/auth/register/options` or `/login/options`: AuthOptionsRequestV1 → `{version:1,challengeId:UUID,options:<SimpleWebAuthn JSON>}`. Registration starts without accountId; register/options returns accountId (UUID) alongside challengeId for client key enrollment, login may omit for discoverable passkeys. POST register/verify or login/verify: AuthVerifyRequestV1 → SessionV1. `response` is exact WebAuthn credential JSON and must be runtime validated by SimpleWebAuthn. register/verify additionally requires enrollment:AccountEnrollmentV1 (client-generated accountCard, verified recoveryWrapper, proof SignedPayloadV1 kind account-enrollment with exact signed body {accountCard,recoveryWrapper}; card accountId must equal allocated challenge account). Server validates proof using card signing key, stores public card and encrypted wrapper only; never receives private keys or recovery secret. Web session uses secure HttpOnly SameSite cookie, response omits token; native returns device-scoped token used in Authorization: Bearer. Session does not unlock vault.
- POST `/v1/auth/recovery/options`: RecoveryOptionsRequestV1 → RecoveryOptionsV1 (public accountCard and encrypted wrappers, never recovery secret). Saved recovery code is `fotoro1.<accountId>.<base64urlRecoverySecret>`; accountId locates bundle even when all passkeys are lost. Client locally unwraps recovery bundle then POST `/v1/auth/recovery/verify`: RecoveryVerifyRequestV1 → SessionV1. signedPayload kind `recovery-session`, accountId matches challenge; exact signed body RecoverySessionProofV1 `{version:1,challengeId,challenge,accountId,client,origin}`. Server validates one-use5min challenge, expected account/client/origin/config and Ed25519 proof from pinned account signing key before issuing session. Existing credentials remain untouched. No authentication is required for encrypted recovery/options; never submit secret to service. Fixture auth routes still return501 REAL_AUTH_REQUIRED.
- GET `/v1/vault` → VaultV1. PUT `/v1/vault/wrappers/:wrapperId`: VaultWrapperV1 → VaultWrapperV1. Wrapper id must match path and verified requires actual client recovery proof via signed enrollment. PRF input is random 32-byte prfSalt, scoped to credentialId, passed as WebAuthn PRF eval.first; PRF output32 is wrapper key. Nonces are random24 per secretbox wrapper. PRF input is retained; PRF output/private keys are not persisted. No PRF: memory-only vault, approval/recovery on reload.
- DELETE `/v1/credentials/:credentialId`: empty body → `{version:1,removed:true}`; deny removing last credential without another verified recovery/device path. Remove only that credential wrapper.
- POST `/v1/devices/enroll`: EnrollDeviceV1 → DeviceChallengeV1, server actor account, random one-use challenge32 and expiresAt +300s. POST `/v1/devices/enroll/:enrollmentId/approve`: DeviceApprovalV1 → DeviceChallengeV1 state approved. Signed body is exactly `{challenge:DeviceChallengeV1,sealedBundle}`, challenge state pending including account/device/box key/origin/challenge/expiry; sealedBundle is account bundle sealed to device box key. POST complete: `{version:1,challenge:Base64Url}` → `{version:1,sealedBundle:Base64Url,challenge:DeviceChallengeV1}` state completed. Reject replay/expiry/wrong origin/account/device. Client verifies signature and expected binding before opening bundle. Persist approved sender signature with sealed bundle and return `signedPayload` in complete response.
- POST `/v1/moments/:momentId/grants/options`: GrantOptionsRequestV1 `{version:1,recipientAccountId,role,access:"ongoing"|"temporary"}` → reserved server-issued GrantV1. Reservation lasts5min; temporary window starts at options issuance and expires precisely +15min using server clock. Client signs exactly this reserved GrantV1; CreateGrantV1 validates reservation, cannot alter expiry or bindings.
- POST `/v1/moments/:momentId/grants`: CreateGrantV1 → GrantV1. Signed body `{grant,envelopes}`. Temporary expiry is exactly15 min from server issuance; ongoing null. Envelopes list explicitly included photoIds (max100); no blanket library access. GET `/v1/grants` → `{version:1,grants:GrantV1[]}` for actor owned/received grants. GET `/v1/grants/:grantId` → `{version:1,grant:GrantV1,envelopes:ShareKeyEnvelopeV1[],manifests:SignedPayloadV1[],cards:AccountCardV1[]}` (current authorized grant only). Client verifies pinned contributor cards, signatures and envelopes before rendering. DELETE `/v1/grants/:grantId` → revoked GrantV1. POST `/v1/grants/:grantId/viewed` → `{version:1,grantId,viewedAt}`; first observed time must persist idempotently.
- POST `/v1/saves`: SaveRequestV1 → SavedPhotoV1. Check active grant + expectedGrantVersion; save has new recipient photoId and signed recipient-owned manifest, immutable source representations and metadataRepresentation reused; metadata key rewrapped for recipient vault. Manifest bindings retain source IDs because ciphertext AAD cannot change without re-encryption. operationId is idempotent scoped to actor. Source photo must be explicitly granted; signature body exactly equals saved manifest. Retention lives independently after revoke.
- POST `/v1/moments/:momentId/contributions`: ContributionV1 → `{version:1,operationId,accepted:number}`. Requires active contributor grant at expected revision. Manifests signed by contributor, encrypted objects already committed, envelopes address other account for same grant. Recipient change page/inbox includes added manifests and envelope; contributor signing identity needs explicit pinning.

Production RP ID fotoro.cloud, allowed origin https://fotoro.cloud; associated domains webcredentials:fotoro.cloud and applinks:fotoro.cloud. Fixture RP localhost, origins http://localhost:4310 and http://127.0.0.1:4310; never allow production credentials on fixture RP/origins.
